This  provides a practical guide to **network diagnostic tools** used for troubleshooting performance issues, discovering devices, and gathering configuration information. It covers **protocol analyzers** (Wireshark), **active scanners** (Nmap), **discovery protocols** (CDP, LLDP), and **bandwidth testing** (speed test sites).


---

### Network Diagnostic Tools Cheat Sheet

This guide covers the most common tools network administrators use to identify problems, discover devices, and measure performance.

---

#### Protocol Analyzers (Packet Captures)

| Tool | Description | Use Cases |
| :--- | :--- | :--- |
| **Wireshark** | Graphical packet capture and analysis tool. Decodes hundreds of protocols. | Deep inspection of conversations; troubleshooting slow applications; security analysis. |
| **tcpdump** | Command‑line packet capture (Linux/macOS/Unix). | Capturing on remote servers without GUI; scripting. |
| **Built‑in device captures** | Switches, routers, firewalls often have built‑in capture or SPAN/mirror ports. | Capturing traffic passing through an infrastructure device. |

**When to use a protocol analyzer:**
- “The network is slow” – you need to see what is actually on the wire (retransmissions, windowing, delays).
- Suspicious traffic (rogue devices, unusual protocols).
- Application‑level troubleshooting (HTTP, database, voice jitter).

**Tip:** For big data analysis, capture to disk and analyse later (forensics, trend analysis).

---

#### Nmap (Network Mapper)

| Aspect | Description |
| :--- | :--- |
| **Type** | Active scanning tool (sends probes to target). |
| **What it finds** | Open ports, running services, operating system, device type, uptime, and more. |
| **Scan modes** | TCP SYN, TCP connect, UDP, ICMP, ARP (layer 2), and many others. |
| **Scripting engine** | Extensible for custom checks (e.g., vulnerability detection, service enumeration). |
| **Output** | Can be formatted as normal text, XML, grep‑able output. |

**Common Nmap Uses:**

| Use Case | Example Command |
| :--- | :--- |
| Single device port scan | `nmap 10.1.10.222` |
| Service version detection | `nmap -sV 10.1.10.222` |
| OS fingerprinting | `nmap -O 10.1.10.222` |
| Scan entire subnet | `nmap 10.1.10.0/24` |
| Layer 2 (ARP) scan (finds all devices on local subnet, even if firewalled) | `nmap -sn 10.1.10.0/24` (uses ARP on same network) |

**Example Output :**
```
Nmap scan report for 10.1.10.222
Host is up.
PORT     STATE    SERVICE
22/tcp   open     ssh
80/tcp   open     http
443/tcp  open     https
548/tcp  open     afp (Apple Filing Protocol)
2049/tcp open     nfs
```

#### Discovery Protocols (CDP and LLDP)

| Protocol | Full Name | Vendor | Information Provided |
| :--- | :--- | :--- | :--- |
| **CDP** | Cisco Discovery Protocol | Cisco (proprietary) | Device ID, IP address, port ID, native VLAN, software version, capabilities. |
| **LLDP** | Link Layer Discovery Protocol | IEEE 802.1AB (vendor‑neutral) | Similar to CDP: device name, port ID, VLAN, MAC address, system description. |

**What You Can Learn Without Logging In:**
- IP address of the switch/router.
- Port name (e.g., GigabitEthernet2).
- Native VLAN.
- Device model and software version.
- Neighbour relationships (network topology).

**Example CDP Decode :**
- IP address: `10.1.10.251`
- Port: `GigabitEthernet2`
- Native VLAN (visible in CDP)
- Device: `Studio-300-28`

**Example LLDP Decode:**
- Switch name: `Studio-300-28`
- Port: `GigabitEthernet2`
- VLAN ID: `10`

**Use Cases:**
- Mapping network topology without credentials.
- Troubleshooting cabling / connectivity (which port is the neighbour connected to?).
- Inventory management (what devices are present?).

**Note:** CDP and LLDP are **layer 2 protocols** and do not require IP connectivity – they work as long as the link is up.

#### Speed Test Sites

| Tool | Notes |
| :--- | :--- |
| **ISP‑provided tests** (Xfinity, AT&T) | Most accurate for your own internet link (end‑to‑end over the ISP's network). |
| **fast.com** | Netflix – simple, no‑frills speed test. |
| **speedtest.net** (Ookla) | Very popular; many servers worldwide; also tests latency and jitter. |
| **SpeedOf.Me** | HTML5‑based; mimics real browser behaviour. |
| **testmy.net** | Provides detailed statistics and historical comparisons. |

**Best Practices:**
- Test at different times of day (peak vs. off‑peak).
- Test before and after network changes to measure improvement.
- Use a local ISP test when possible (eliminates external routing variables).

**Limitations:**
- External speed tests are limited by the **slowest link** between you and the test server.
- Your ISP may prioritise speed test traffic, giving optimistic results.

#### Diagnostic Workflow (“The network is slow”)

| Step | Tool / Action |
| :--- | :--- |
| 1. Check if it is really the network | Run a local speed test (iPerf between two internal devices). |
| 2. Check interface counters | SNMP, `show interfaces` (errors, drops, CRC). |
| 3. Check utilisation | SNMP, NetFlow, switch port statistics (is the link saturated?). |
| 4. Check for wireless interference | Wi‑Fi analyser, heat map, channel utilisation. |
| 5. Discover what devices are on the network | Nmap scan – is there a rogue device causing congestion? |
| 6. Check neighbour switch information | LLDP / CDP – verify cabling and expected connections. |
| 7. Capture traffic | Wireshark – look for retransmissions, zero‑window, unusual delays. |
| 8. Test internet bandwidth | Speed test (ISP preferred). |

---

#### Key Takeaways

| Takeaway | Explanation |
| :--- | :--- |
| **Wireshark (protocol analyser) gives deep insight** | See the actual packets – delays, retransmissions, application behaviour. |
| **Nmap discovers open ports and OS** | Active scanning finds rogue devices and unexpected services. |
| **CDP/LLDP reveal switch configuration** | Learn IPs, VLANs, and neighbour relationships without logging in. |
| **Speed tests measure real throughput** | Use consistently (same site, same time of day) for comparisons. |
| **“Network is slow” is often not the network** | Check server, database, storage, and application before blaming the network. |
| **Combine multiple tools** | No single tool gives the full picture – use protocol analyser + scanner + discovery + speed test. |
