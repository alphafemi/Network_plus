### Network Performance Troubleshooting Cheat Sheet

This guide covers the causes of slow network performance, key metrics (bandwidth, throughput, latency, jitter, packet loss), and diagnostic approaches.

---

#### Congestion and Contention

| Problem | Cause | Consequence |
| :--- | :--- | :--- |
| **Congestion** | Multiple high‑bandwidth flows trying to exit a slower link (e.g., two 1 Gbps flows into one 1 Gbps uplink). | Packets queue in buffers → buffer fills → packets are **dropped**. |

**Solution Options:**
- Increase link speed (e.g., 1 Gbps → 10 Gbps uplink).
- Reduce traffic (rate limiting, QoS, traffic shaping).

---

#### Bottlenecks

| Aspect | Description |
| :--- | :--- |
| **What it is** | A point in the system where the throughput is lower than other segments, limiting overall performance. |
| **Possible locations** | CPU, memory, disk (HDD/SSD), network link, software application, database. |

**Example (from video):**

| Phase | Before Fix | After Fix |
| :--- | :--- | :--- |
| Database time | High (bottleneck) | Normal |
| Total transaction response | ~1500–1750 ms | ~500 ms |

**Takeaway:** The bottleneck was the **database server**, not the network. Once the database was optimised, response time dropped dramatically.

---

#### Key Performance Metrics

| Metric | Definition | Measurement Unit | Tool / Method |
| :--- | :--- | :--- | :--- |
| **Bandwidth** | Theoretical maximum data rate of a link. | bits per second (bps) | Link specification (e.g., 1 Gbps). |
| **Throughput** | Actual amount of data successfully transferred over time. | bps or bytes per second (Bps) | iPerf, SNMP, NetFlow, switch counters. |
| **Latency** | Delay between request and response (one‑way or round‑trip). | milliseconds (ms), microseconds (µs) | ping, traceroute, packet capture timestamps. |
| **Jitter** | Variation in packet arrival times (delay variance). | ms | VoIP monitoring tools, packet capture. |
| **Packet Loss** | Percentage of packets that never reach their destination. | percentage (%) | ping, SNMP (ifOutDiscards), application logs. |

---

#### Latency (Delay)

| Type | Description | Typical Cause |
| :--- | :--- | :--- |
| **Propagation delay** | Time for signal to travel over distance (speed of light / fibre). | Long distance (e.g., transcontinental). |
| **Serialisation delay** | Time to put bits onto a physical link. | Slower link speed (e.g., 10 Mbps instead of 1 Gbps). |
| **Queuing delay** | Time packet waits in buffer before being forwarded. | Congestion. |
| **Processing delay** | Time device takes to inspect packet and make forwarding decision. | Slow CPU, ACL processing, encryption. |

**Diagnostic Tip:** Use `traceroute` to see latency per hop. Packet capture at multiple points gives microsecond granularity.

---

#### Jitter (Delay Variation)

| Aspect | Description |
| :--- | :--- |
| **What it is** | The variability in the arrival time of consecutive packets. |
| **Low jitter (good)** | Packets arrive at regular, predictable intervals. |
| **High jitter (bad)** | Packets arrive in bursts with long gaps in between. |
| **Impact** | Voice/video calls: clicks, stuttering, robotic audio; real‑time applications degrade. |

**Jitter Visualisation:**
- **Low jitter:** packet1 →(10ms)→ packet2 →(10ms)→ packet3 →(10ms)→ packet4
- **High jitter:** packet1 →(5ms)→ packet2 →(50ms)→ packet3 →(5ms)→ packet4

**Mitigation:** Jitter buffers (real‑time applications), QoS (prioritise real‑time traffic), increase bandwidth, reduce congestion.

---

#### Packet Loss

| Cause | Description |
| :--- | :--- |
| **Congestion** | Buffer overflow (most common). |
| **Corruption** | Bad cable, interference, faulty SFP (FCS errors → discard). |
| **Outage** | Link down, routing loop, misconfigured ACL. |
| **Wireless interference** | High noise, low SNR, retransmissions. |

**Effect on applications:**
- **TCP:** Recovers via retransmission (slower throughput, increased latency).
- **UDP (VoIP, video):** Packets are lost forever (clicks, stutter, frozen frames). No retransmission.

#### Diagnostic Process for "Slow Network"

| Step | Action | What to Look For |
| :--- | :--- | :--- |
| 1 | Measure end‑to‑end throughput (iPerf). | Actual throughput vs. expected bandwidth. |
| 2 | Check interface counters (CRC, drops). | Physical errors or discards. |
| 3 | Measure latency (ping, traceroute). | High delay or varying delay. |
| 4 | Check for congestion (utilisation percentage). | Sustained >80% utilisation → potential drops. |
| 5 | Identify bottleneck (CPU, disk, database, link). | Use monitoring tools (NetFlow, SNMP, application profiling). |
| 6 | Verify QoS configuration (if applicable). | Is real‑time traffic being queued properly? |

---

#### Tools for Performance Measurement

| Tool | Use Case |
| :--- | :--- |
| **iPerf / iPerf3** | Measure raw TCP/UDP throughput between two endpoints. |
| **ping** | Round‑trip latency and packet loss (basic). |
| **traceroute** | Path discovery and per‑hop latency. |
| **SNMP** (MIB‑II) | Interface utilisation, error counters, discards. |
| **NetFlow / sFlow / IPFIX** | Traffic volume by source, destination, protocol, application. |
| **Packet capture (Wireshark, tcpdump)** | Granular latency, jitter, retransmissions, delays per packet. |
| **Application Performance Monitoring (APM)** | Response time breakdown (network vs. server vs. database). |

#### Example: Web Transaction Bottleneck Analysis

| Metric | Before | After | Implication |
| :--- | :--- | :--- | :--- |
| Database time | High | Low | Bottleneck was database processing. |
| Network round‑trip | Low | Low | Network was not the cause. |
| Total response time | 1500–1750 ms | 500 ms | Fixing database resolved the user complaint. |

**Key Point:** "Slow network" often is not the network at all. Always check **server, storage, application, and database** as potential bottlenecks.

---

#### Key Takeaways

| Takeaway | Explanation |
| :--- | :--- |
| **Bandwidth is theoretical; throughput is real** | Actual transfer rate is almost always lower than link speed due to overhead, congestion, and other factors. |
| **Congestion causes drops** | Too much traffic for a link → queues fill → packets discarded. |
| **Latency is delay** | Use traceroute to find where delay is introduced. |
| **Jitter is variance in delay** | High jitter disrupts real‑time applications (VoIP, video). |
| **Packet loss is the enemy of good performance** | TCP recovers slowly; UDP loses data forever. |
| **Slow network ≠ always a network problem** | Server, database, storage, or CPU may be the real bottleneck. |
| **Measure, don’t guess** | Use iPerf, traceroute, packet captures, and interface counters to identify the root cause. |
