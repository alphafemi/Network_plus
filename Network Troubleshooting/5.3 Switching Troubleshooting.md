### Spanning Tree Protocol (STP) and Switching Troubleshooting Cheat Sheet

This guide covers STP operation, BPDUs, root bridge election, port states, and common switch issues (VLANs, ACLs).

---

#### Why Spanning Tree is Needed

| Problem | Cause | Consequence |
| :--- | :--- | :--- |
| **Layer‑2 loop** | Two (or more) paths between switches (e.g., accidental extra cable). | Broadcast/multicast frames circulate indefinitely; MAC table instability; network saturation → complete outage. |

**Note:** IP packets have a Time to Live (TTL) field to prevent looping at layer 3. Ethernet frames have **no such mechanism** at layer 2. STP prevents loops at the switch level.

---

#### Bridge Protocol Data Units (BPDUs)

| Aspect | Description |
| :--- | :--- |
| **What they are** | Layer‑2 multicast frames exchanged between switches to share STP information. |
| **Frequency** | Sent every **2 seconds** by default (Cisco). |
| **Purpose** | Elect root bridge, detect topology changes, prevent loops. |
| **Failure detection** | If a switch misses **3 BPDUs** (6 seconds), the link is considered down, and STP recalculates the topology. |

---

#### Root Bridge Election

| Rule | Explanation |
| :--- | :--- |
| **Bridge ID (BID)** = Priority (4 bits) + MAC address (12 bits). |
| **Lowest bridge ID wins** | The switch with the smallest BID becomes the **root bridge**. |
| **Priority range** | 0 – 61,440 (in increments of 4096 on many platforms). |
| **Tie‑breaker** | If priorities are equal, the lowest **MAC address** becomes the root bridge. |

**Best Practice:** Manually set a low priority (e.g., 4096) on the switch you want as root. Do not rely on MAC‑address tie‑breakers.

---

#### STP Port Roles and States

| Port Role | Description |
| :--- | :--- |
| **Root port** | The port on a non‑root switch that provides the **best path to the root bridge** (one per switch). |
| **Designated port** | The port on a segment that is **closest to the root bridge** (one per segment). |
| **Blocked (Alternate) port** | Port that is **administratively blocked** by STP to prevent a loop. |

**Port States (Cisco STP progression):**

| State | Listens to BPDUs? | Learns MACs? | Forwards traffic? | Stable? |
| :--- | :--- | :--- | :--- | :--- |
| **Blocking / Discarding** | Yes | No | No | Final state for loop prevention. |
| **Listening** | Yes | No | No | Transient during STP recalculation. |
| **Learning** | Yes | Yes | No | Transient; building MAC table. |
| **Forwarding** | Yes | Yes | Yes | Final state for active ports. |
| **Disabled** | No | No | No | Admin‑shutdown port. |

---

#### STP Recovery from Link Failure (Example)

| Step | Action |
| :--- | :--- |
| **1** | Primary link fails (e.g., Switch A – Switch B). |
| **2** | Switch misses 3 BPDUs on that link (6 seconds). |
| **3** | STP initiates recalculation. |
| **4** | Previously blocked alternate port transitions: Listening → Learning → Forwarding. |
| **5** | Traffic resumes via the alternate path. |

**Result:** Redundant paths provide automatic failover without user intervention.

#### VLAN Configuration Issues

| Symptom | Likely Cause |
| :--- | :--- |
| Device receives IP address (DHCP) but cannot communicate with other devices **on the same subnet**. | Switch port is in the **wrong VLAN**. |

**Troubleshooting Steps:**

1. Check the VLAN assignment of the switch port (e.g., `show interface status`).
2. If the port is in VLAN 100, but the device expects VLAN 254, either:
   - Move the device to a port already configured for VLAN 254, or
   - Reconfigure the switch port to the correct VLAN.

**Note:** Switches may drop traffic between devices on different VLANs even if they share the same IP subnet. VLANs are layer‑2 separation; a router (or layer‑3 switch) is required to route between VLANs.

---

#### Access Control Lists (ACLs) on Switches

| Aspect | Description |
| :--- | :--- |
| **Effect** | ACLs can block traffic even if IP addressing and VLANs are correct. |
| **Default behaviour** | Many devices have an **implicit deny** at the end of every ACL. If no “permit” rules match, traffic is dropped. |
| **Empty ACL** | Blocks **all** traffic through the interface. |

**Best Practices for ACL Changes (Remote Access):**
- **Disable the ACL** before editing (if possible) to avoid locking yourself out.
- **Apply ACLs carefully** – an incorrectly placed ACL can cut off management access (SSH, SNMP).
- **Test with an allow‑all first** when adopting an existing switch.

---

#### Troubleshooting Flow for Switching Issues

| Step | Action |
| :--- | :--- |
| **1** | Check link lights / physical connectivity. |
| **2** | Verify switch port VLAN assignment. |
| **3** | Verify device receives correct IP address / subnet (DHCP). |
| **4** | Ping another device on the **same** VLAN/subnet. If fails → layer‑2 issue (VLAN, STP blocking, cable). |
| **5** | Ping the default gateway. If fails → check trunk, router, or layer‑3 interface. |
| **6** | Review ACLs on switches and routers along the path. |
| **7** | Check STP port state (forwarding / blocking / err‑disabled). |
| **8** | Examine interface counters (CRC, runts, giants, drops). |

---

#### Key Takeaways

| Takeaway | Explanation |
| :--- | :--- |
| **STP prevents layer‑2 loops** | Without STP, a redundant path will crash the network. |
| **BPDUs are heartbeat messages** | Sent every 2 seconds; 3 missed BPDUs = link failure. |
| **Root bridge is elected by lowest bridge ID** | Manually set priority to control the root. |
| **STP port states transition** | Blocking → Listening → Learning → Forwarding (or Blocking again). |
| **Wrong VLAN = no communication** | Even with correct IP address, devices on different VLANs cannot communicate directly. |
| **ACLs can silently drop traffic** | Check for ACLs when routing and switching look correct. |
| **Always have a recovery plan** | Editing ACLs remotely can lock you out. |
